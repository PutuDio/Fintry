# ADR-002: Persistence Model and Database Connection

- **Status:** Accepted
- **Date:** 2026-10-08
- **Related:** `AGENTS.md`, `docs/PRD.md`, `docs/domain_rules.md`, `docs/tech_stack.md`, `docs/architecture_decisions/ADR-001.md`, `docs/architecture_decisions/ADR-003.md`

## 1. Context

ADR-001 fixed the stack (Next.js, TypeScript, PostgreSQL, Drizzle, Zod) and the boundary *"AI interprets. Application validates. Domain calculates. Database persists."* It left the exact schema to the database design phase (`tech_stack.md` section 9).

This ADR records the final persistence model and the database connection policy ahead of the schema implementation. It contains no Drizzle schema and no migrations.

Requirements driving the decisions:

- financial mutations are atomic and safe under concurrent requests
- balances and net worth are deterministic and derived by application code
- history is auditable: reversal never deletes financial records
- repeated chat submissions create one mutation
- user data is isolated
- no vendor lock-in for the database driver or provider

## 2. Decision

### 2.1 Conventions

- Primary keys: `uuid`, `gen_random_uuid()` default.
- Timestamps: `timestamptz`, default `now()`.
- Money: `BIGINT` IDR, no floating point (ADR-001 section 7). In TypeScript, money is `bigint` (Drizzle `bigint` in `bigint` mode) and is serialized as a string at boundaries.
- `transaction_date`: `date` (resolved calendar date, Asia/Jakarta); Drizzle `date` in string mode.
- Enums: PostgreSQL enums through Drizzle `pgEnum`.
- Every user-owned table has `user_id NOT NULL` referencing `users(id)`.
- Domain and financial tables use `ON DELETE RESTRICT` (section 2.9).

### 2.2 Tables

`users` is owned by Better Auth (ADR-003) and receives no domain columns.

| Column | Type | Notes |
|---|---|---|

| user_id | uuid NOT NULL | FK → users, RESTRICT |
| type | enum | `INCOME`, `EXPENSE`, `TRANSFER` |
| amount | bigint NOT NULL | always positive |
| source_asset_id | uuid NULL | |
| destination_asset_id | uuid NULL | |

| created_at, updated_at | timestamptz | |

- Composite FKs: `(source_asset_id, user_id)` and `(destination_asset_id, user_id)` → `assets(id, user_id)`; `(category_id, user_id)` → `categories(id, user_id)`; `(replaces_transaction_id, user_id)` → `transactions(id, user_id)`. All RESTRICT.

- CHECK `amount > 0`.

- Indexes: `(user_id, transaction_date DESC, created_at DESC)`; `(user_id, type, transaction_date) WHERE status = 'ACTIVE'`. Filter indexes by asset and category (partial, `WHERE ... IS NOT NULL`) ship with the filtering feature.
- Investment purchase has no dedicated column: it is a `TRANSFER` whose destination is an `INVESTMENT` asset.

### 2.3 Relationships

```text
users 1─N assets ─┬─< transactions (as source)
                  ├─< transactions (as destination)
                  └─< asset_adjustments
users 1─N categories ──< transactions (0..1)
users 1─N pending_intents
users 1─N idempotency_keys
users 1─N audit_log      (polymorphic: entity_type + entity_id)
transactions 0..1 ── replaces ──> transactions
```

Net worth is not stored. It is `SUM(current_value)` over the user's active assets, computed on read.

### 2.4 Atomic transaction flow

Every financial command runs in one interactive database transaction:

```text
BEGIN
 1. INSERT idempotency_keys ... ON CONFLICT DO NOTHING
    (if the key already exists: return the stored result)
 2. lock pending_intents row          (when resolving a pending intent)
 3. lock transactions row             (void, edit, replacement)
 4. lock assets rows, ordered by id   (SELECT ... FOR UPDATE)
 5. engine (pure function) computes new values from the locked rows
 6. UPDATE assets
 7. INSERT transactions / asset_adjustments, or set status = VOIDED
 8. INSERT audit_log
 9. UPDATE idempotency_keys.result; update pending_intents status
COMMIT   (any error: ROLLBACK, no success response)
```

The lock order in steps 1 to 4 is mandatory. The engine reads asset values only after locking them. READ COMMITTED isolation plus explicit row locks is sufficient; SERIALIZABLE is not required.

### 2.5 Concurrency and idempotency

- Concurrent commands on the same asset serialize on the asset row lock.
- Deadlock and lock failures map to a "concurrency conflict" error. The retry policy is defined at implementation time.
- The idempotency row is inserted in the same transaction as the mutation, so it exists only if the mutation committed. A concurrent duplicate waits on the unique index, then receives the stored result. The same key with a different `request_hash` is rejected.
- A clarification answer is a new submission with a new key.

### 2.6 Void, edit, and replacement

Defined in `domain_rules.md` sections 17.1 and 17.2. In summary:

- Void sets `status = VOIDED` and `voided_at`, reverses balances, and writes audit. No un-void. Rejected if it would make an asset negative or if it touches an inactive asset.
- Direct edit: `description`, `category_id`, `transaction_date`. Audit action `TRANSACTION_UPDATED`.
- Financial fields (`type`, `amount`, `source_asset_id`, `destination_asset_id`): void plus replacement in one database transaction, linked by `replaces_transaction_id`.
- `VOIDED` transactions are not edited.
- `asset_adjustments` are append-only: no update, void, or delete.

### 2.7 Pending intents

One `PENDING` row per user, 10-minute TTL, deterministic routing, and final states never reopened (`tech_stack.md` section 15). The transaction that creates a new pending intent first transitions any existing `PENDING` row (expired or superseded) in the same transaction.

### 2.8 User isolation

- The authenticated `userId` comes from the server-side session only.
- Repositories require `userId` and scope every query.
- Composite FKs make the database reject cross-user references.
- Isolation tests are mandatory.
- **Row Level Security is deferred from the MVP.** It can be added later without a schema change.
- **Database-level append-only triggers are deferred from the MVP.** Compensating controls: repositories expose no update or delete path for `transactions` (beyond the defined edit and void commands), `asset_adjustments`, and `audit_log`, and tests verify it.

### 2.9 Deletion

- Domain and financial tables use `ON DELETE RESTRICT`.
- Account deletion and the purge procedure are deferred from the MVP and will be defined separately.
- Better Auth's `sessions` and `accounts` tables may cascade, because they hold no financial data (ADR-003).

### 2.10 Database driver and connection

- Driver: **`pg` (node-postgres)** with `drizzle-orm/node-postgres`. The `postgres` package is removed; `pg` and `@types/pg` are added.
- One `Pool` instance, created in `infrastructure/db`.
- Financial mutations use interactive transactions with `SELECT ... FOR UPDATE` (Drizzle `.for('update')`).
- `neon-http` must not be used for financial mutations: it does not support interactive transactions.
- No session-level advisory locks and no session-level `SET`, so the engine works behind a PgBouncer-style transaction pooler.
- Runtime connections may use a pooler. Migrations use a direct connection.
- Database code runs on the Node.js runtime, not Edge.
- **Drizzle Kit is the only migration tool.** Better Auth's migration CLI is not used.

## 3. Rationale

- The ledger is split because opening balances, adjustments, and valuations are not cashflow (domain rules sections 7 to 9).
- `current_value` is stored because balance reads are the hot path, and it is kept consistent by row locks plus a reconciliation test (stored value equals opening balance plus active ledger plus adjustment deltas). Net worth is not stored, to avoid duplicated derived state.
- A separate `idempotency_keys` table covers every command (void, edit, asset creation, pending resolution), not only inserts into ledger tables, and stores the response for replays.
- Composite foreign keys give database-level isolation without RLS.
- `pg` is the driver because it is the most portable choice. Both drivers can run interactive transactions and row locks, so this is a portability tie-breaker rather than a capability gap: `postgres` uses named prepared statements by default, which needs `prepare: false` on some transaction poolers, and `pg` has an API-compatible WebSocket pool in Neon's serverless driver as a fallback path. Nothing depended on the driver when it was replaced.

## 4. Alternatives Considered

| Alternative | Why rejected |
|---|---|
| `postgres` (postgres.js) driver | Capable, but prepared-statement defaults add pooler-specific configuration, and there is no API-compatible serverless fallback. Replacement cost was near zero. |
| `neon-http` driver | No interactive transactions; unusable for lock-compute-update. |
| Edit financial fields in place and recompute | Higher risk of balance bugs and a harder audit story. |
| Every edit as void plus replacement | Noisy history for description or category corrections. |
| Voidable adjustments | Breaks the `value_before` / `value_after` chain when the voided row is not the latest. |
| `idempotency_key` column on each mutation table | Covers only inserts, stores no response, duplicates the mechanism. |
| Stored net worth or snapshots | Duplicated derived state with no consistency strategy. |
| Allow negative balances | Rejected by product decision; silent negative balances distort net worth. |
| Session-level advisory locks | Not reliable behind transaction poolers. |
| `ON DELETE CASCADE` on financial tables | One bad delete could erase financial history without a trace. |
| Triggers and RLS in the MVP | Deferred, not rejected (section 2.8). |

## 5. Consequences

### Positive

- deterministic, auditable financial state
- concurrency safety through explicit row locks and a fixed lock order
- one idempotency mechanism for all commands
- cross-user references rejected by the database
- the driver and provider can change without touching the domain

### Negative

- more tables and constraints to write and test
- `current_value` is derived state that needs a reconciliation test
- void or edit can be rejected when a later state would make a balance negative; the chat response must explain this
- adjustments cannot be undone, only corrected by a new adjustment
- append-only and isolation guarantees rely on repository discipline and tests until triggers and RLS are added
- account deletion is not possible until a purge procedure exists

## 6. Mandatory Rules

1. Financial commands follow the flow and lock order in section 2.4.
2. Asset values never become negative; the engine rejects, and the database CHECK is a second layer.
3. Ledger and audit rows are never physically deleted by application code.
4. `asset_adjustments` are never updated, voided, or deleted.
5. Financial fields of a transaction are never edited in place.
6. Inactive assets are not used for new transactions, adjustments, or valuations, and void on a transaction touching an inactive asset is rejected.
7. Every user-owned query is scoped by the authenticated `userId`.
8. Migrations run through Drizzle Kit over a direct connection.
9. The `postgres` package and HTTP-only drivers are not used for financial mutations.
10. Net worth and dashboard totals come from backend queries, not from the client.

## 7. Migration and Upgrade Risks

- **Adding CHECK constraints later** fails if data already violates them; the negative-balance CHECK ships in the first migration.
- **Changing a primary key type** (for example `uuid` to `text`) later touches every table and composite FK. The UUID gate in ADR-003 exists to prevent this.
- **Composite FKs** require `UNIQUE (id, user_id)` on every parent table; omitting it from a parent breaks the child constraint.
- **Partial unique index on `pending_intents`** does not consider `expires_at`; code must transition old rows first.
- **Poolers:** transaction-mode poolers do not support session state. Any future use of `SET`, `LISTEN/NOTIFY`, or session advisory locks needs a new decision. RLS via per-transaction settings must be re-verified against the pooler before it is enabled.
- **Drizzle ORM is pre-1.0 (0.x):** minor upgrades can change behavior. Pin the version and read release notes before upgrading.
- **Driver replacement** (for example to a WebSocket pool) must keep interactive transactions and row locking.
- **Idempotency table growth:** a retention policy is needed before production.
- **Destructive schema changes** require explicit approval (`rules.md` section 6).

## 8. Left to the Schema-Implementation Step

These are not decided here and must not be assumed:

- exact enum, constraint, and index names
- whether the asset name unique rule covers inactive assets (the default above is unique across all of a user's assets, so an inactive asset's name stays reserved because there is no reactivation)
- whether to add a CHECK `(is_active OR current_value = 0)` as a second layer for the deactivation rule
- idempotency key retention period
- whether filter indexes ship in the first migration
- the implementation form of the case-insensitive unique rule (expression index versus generated column)

## 9. Final Decision

Fintry uses the persistence model above with PostgreSQL, Drizzle, and the `pg` driver, a deterministic engine, interactive transactions with row locking, a separate idempotency table, void-based reversal, append-only adjustments, and `ON DELETE RESTRICT`. RLS and database-level append-only triggers are deferred from the MVP with the compensating controls listed in section 2.8.

**Core invariant:**

> AI interprets. Application validates. Domain calculates. Database persists.
