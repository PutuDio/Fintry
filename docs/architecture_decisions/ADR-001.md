# ADR-001: Core Architecture and Provider-Agnostic AI Boundary

- **Status:** Accepted
- **Date:** 2026-10-06
- **Related:** `AGENTS.md`, `docs/PRD.md`, `docs/domain_rules.md`, `docs/project_overview.md`, `docs/tech_stack.md`

## 1. Context

Fintry is a chat-first personal finance application. It must process natural-language financial input while maintaining deterministic, auditable financial state.

Important constraints:

- financial mutations must be atomic
- concurrent requests must not corrupt financial state
- balances and net worth must be deterministic
- LLM output must be schema-validated
- LLMs must not directly mutate financial state
- user financial data must remain isolated
- financial history must remain auditable
- AI providers must be replaceable
- the MVP should be practical for a solo developer
- operating cost should remain low while free-tier AI services are used

The project intentionally uses multiple AI providers, coding agents, free-tier models, and potentially routing services such as OpenRouter. Therefore, no single AI provider may become a core application dependency.

## 2. Decision

Fintry adopts:

```text
Next.js + TypeScript + PostgreSQL + Drizzle + Zod
+ Tailwind CSS + shadcn/ui + Vitest + Playwright
```

The application uses:

```text
Presentation → Application → Domain → Infrastructure
```

The financial domain is deterministic and independent of AI providers.

AI is accessed through an internal provider abstraction:

```text
AIProvider
├── parseTransaction()
├── classifyIntent()
└── generateResponse()
```

The main flow is:

```text
User
  ↓
Chat UI
  ↓
AI Provider Adapter
  ↓
Structured Intent
  ↓
Zod Validation
  ↓
Intent Validator
  ↓
Asset Resolver
  ↓
Application Command
  ↓
Financial Engine
  ↓
Repository
  ↓
PostgreSQL Transaction
```

## 3. Rationale

### 3.1 Next.js + TypeScript

A single full-stack application reduces MVP overhead and keeps UI, application contracts, and AI integration in one language.

### 3.2 PostgreSQL

PostgreSQL provides the transactions, locking, constraints, foreign keys, indexes, and data types required by the financial domain.

### 3.3 Drizzle

Drizzle provides typed database access while keeping PostgreSQL behavior explicit enough for financial transaction and locking requirements.

### 3.4 Zod

LLM output is untrusted input. Zod provides runtime validation before structured intent enters application logic.

The LLM may extract `"25rb"` or `"kemarin"`, but deterministic application code converts those values into authoritative amount/date values.

## 4. AI Provider Strategy

Fintry is **provider agnostic**.

During the free/MVP phase, the project may use:

- different coding agents
- different hosted models
- free-tier models
- OpenRouter or similar routing services
- local models where practical
- different models for different workloads

Provider SDKs belong only in the infrastructure/AI layer.

Examples:

```text
infrastructure/ai/
├── provider.ts
├── openrouter/
├── provider-a/
├── provider-b/
└── mock/
```

Changing the provider or model must not require changes to financial domain logic.

Model selection is an operational decision based on cost, speed, structured-output quality, and task complexity.

## 5. Financial Safety Boundary

The mandatory rule is:

> **AI interprets. Application validates. Domain calculates. Database persists.**

The AI must not:

- execute financial SQL
- directly mutate financial records
- calculate authoritative balances
- bypass authorization or validation
- bypass transaction boundaries
- claim a financial mutation succeeded without an application result

## 6. Data Integrity

Financial mutations use database transactions:

```text
BEGIN
  ↓
validate
  ↓
lock relevant records
  ↓
deterministic calculation
  ↓
update state
  ↓
write financial record
  ↓
write audit information
  ↓
COMMIT
```

Failure results in `ROLLBACK`.

Idempotency is required to prevent repeated chat requests from creating duplicate mutations.

## 7. Money Representation

The MVP uses IDR and integer monetary values stored as `BIGINT`.

```text
Rp25.000 → 25000
```

Authoritative financial calculations must not use JavaScript floating-point arithmetic.

Multi-currency requires a separate ADR because it changes valuation, exchange-rate, net-worth, and schema semantics.

## 8. Alternatives Considered

### Separate React SPA + NestJS/Fastify

Not selected for MVP because two projects and deployment units add overhead without a current product requirement for that separation.

### Laravel + Inertia

Technically viable, especially for a Laravel-oriented workflow, but TypeScript across UI/application/AI contracts provides better consistency for this project.

### Next.js + Supabase as core architecture

Not selected as the architectural center because strict financial rules should remain explicit and testable in application/domain code rather than being distributed across application code, RLS, SQL functions, and provider-specific APIs.

Managed PostgreSQL services can still be used as infrastructure.

### Direct LLM-to-database agent

Rejected because it makes financial correctness dependent on probabilistic model behavior and creates unacceptable risks around incorrect balances, duplicate transactions, unauthorized mutations, partial updates, and auditability.

## 9. Consequences

### Positive

- one primary language
- fast MVP development
- strong transaction guarantees
- provider-independent AI architecture
- easy switching among free AI providers/models
- deterministic financial calculations
- testable domain logic
- lower vendor lock-in

### Negative

- more explicit domain/application code
- AI output requires validation and normalization
- provider adapters add abstraction
- concurrency and PostgreSQL transactions require careful implementation
- autonomous LLM mutation is intentionally restricted

These costs are intentional because financial correctness has priority over minimum implementation complexity.

## 10. Mandatory Rules

1. Financial state is never mutated directly by an LLM.
2. AI providers are accessed through an internal adapter/interface.
3. AI output is treated as untrusted input.
4. Structured AI output is validated with Zod.
5. Amount/date normalization is deterministic application logic.
6. Financial mutations use database transactions.
7. Concurrency-sensitive operations use appropriate database locking.
8. Duplicate financial requests are protected by idempotency.
9. User ownership is enforced at application/repository boundaries.
10. Reversal does not physically delete financial history.
11. Dashboard values come from backend state.
12. Provider-specific SDKs stay inside infrastructure/AI.
13. Changing AI providers must not require financial-domain changes.
14. Changing deployment providers must not require financial-domain changes.

## 11. Future Reconsideration

Revisit this ADR if Fintry requires multi-currency accounting, multiple independent frontends, independent backend scaling, event-driven architecture, real-time synchronization, bank synchronization, advanced portfolio management, offline-first financial operation, or a substantially different AI interaction architecture.

Such changes should be documented through new ADRs rather than silently modifying this decision.

## 12. Final Decision

Fintry will use a **Next.js + TypeScript + PostgreSQL + Drizzle + Zod** architecture with a deterministic financial engine and a provider-agnostic AI integration layer.

AI providers/models may be switched according to availability, cost, capability, and task requirements without changing the financial domain.

**Core invariant:**

> AI interprets. Application validates. Domain calculates. Database persists.
