# ADR-003: Authentication

- **Status:** Accepted
- **Date:** 2026-10-08
- **Related:** `AGENTS.md`, `docs/PRD.md`, `docs/tech_stack.md`, `docs/architecture_decisions/ADR-001.md`, `docs/architecture_decisions/ADR-002.md`

## 1. Context

`tech_stack.md` section 19 fixed email + password authentication and required the implementation to stay replaceable, but did not choose a library. The choice affects the `users` table, the type of `user_id` in every domain table, and the migration pipeline.

Constraints:

- Next.js App Router, TypeScript, PostgreSQL, Drizzle
- email + password, session-based
- user IDs are PostgreSQL `uuid` (every domain table references `users(id)`)
- solo MVP, low maintenance
- no vendor lock-in; data stays in the project's own PostgreSQL
- PRD section 18: password hashing, secure session handling, rate limiting

## 2. Decision

**Better Auth** is the authentication library.

### 2.1 Configuration

- Version pinned **exactly** (currently 1.7.7); no range.
- Email + password.
- **Database sessions** in PostgreSQL. Session cookie cache is not enabled, so revocation is immediate.
- Rate limiting for authentication endpoints uses Better Auth's built-in limiter with `database` storage, so it works on serverless hosts.
- User IDs are **UUID**: `advanced.database.generateId` is set to `"uuid"`; on PostgreSQL adapters the database generates the UUID. The auth tables are defined in the project's own Drizzle schema with `uuid` columns and `defaultRandom()`.
- The Better Auth schema generator is a **reference only**. The authoritative table definitions are in the project's Drizzle schema.
- **Drizzle Kit is the only migration tool.** Better Auth's migration command is not used.

### 2.2 Tables owned by Better Auth

`users`, `sessions`, `accounts`, `verifications`, and the rate-limit table. Column names follow the installed version's schema (mapped to the project's plural table names).

- No domain columns are added to `users`. No extra columns are added in the MVP.
- The password hash is stored in `accounts`, not in `users`.
- `verifications` exists because the core schema requires it; it is unused in the MVP.

### 2.3 Boundary

- All authentication code lives in `infrastructure/auth`.
- Application and domain code only know `userId` (a UUID string).
- Authorization is checked in the application layer on every operation. A routing/proxy-level check is not sufficient on its own.

### 2.4 Foreign keys

- Domain and financial tables reference `users(id)` with `ON DELETE RESTRICT` (ADR-002).
- `sessions` and `accounts` reference `users(id)` and may cascade, because they hold no financial data.
- Composite FKs `(child_fk, user_id) → parent(id, user_id)` are unchanged.

### 2.5 Registration and `name`

Better Auth's core schema requires `name` (not null). The registration form asks for **email and password only**. The server derives `name` from the part of the email before `@` (at most 100 characters). `name` is never used by domain logic and is not shown in chat.

### 2.6 Not enabled in the MVP

Email verification, OAuth/social providers, MFA, account deletion, email change, all plugins, and stateless (cookie-only) sessions.

## 3. Rationale

- Database sessions with email/password, a Drizzle adapter, and a built-in rate limiter match the requirements without custom security code.
- Data (users, hashes, sessions) stays in the project's PostgreSQL.
- Future needs (MFA in PRD P2) are available as plugins without changing the architecture.
- The `infrastructure/auth` boundary keeps the library replaceable.

## 4. Alternatives Considered

| Alternative | Why rejected |
|---|---|
| **Auth.js (NextAuth v5)** with the Drizzle adapter | The Auth.js project is now maintained by the Better Auth team for security patches and urgent fixes only, and Better Auth is recommended for new projects. The Credentials provider does not support database sessions out of the box, so email/password forces JWT sessions, which conflicts with the database-session requirement. |
| **Self-implemented sessions** (the pattern Lucia now teaches; Lucia v3 is deprecated as a library) | Full control and zero lock-in, but password hashing, token handling, cookie flags, CSRF, login rate limiting, and user-enumeration protections would all be written and maintained by one developer in a financial application. |
| **Hosted providers** (for example Clerk, Supabase Auth) | User data and sessions live at a vendor, which conflicts with the lock-in criterion. ADR-001 also rejected a Supabase-centered architecture. |

## 5. Consequences

### Positive

- no custom password or session security code
- UUID user IDs stay compatible with the persistence model
- rate limiting is built in
- the library is replaceable behind `infrastructure/auth`

### Negative

- dependency on a young, fast-moving library
- extra tables outside the domain model
- `name` is required by the library even though the product does not use it
- password hash format depends on the library

## 6. Mandatory Rules

1. Authentication code is only in `infrastructure/auth`.
2. Application and domain code do not import Better Auth.
3. `userId` is a UUID and comes only from the server-side session.
4. Better Auth is pinned to an exact version.
5. Features listed in section 2.6 stay disabled until a new decision enables them.
6. Migrations come only from Drizzle Kit.
7. Before upgrading Better Auth, compare the schema generator's output for the new version with the project's table definitions and run the UUID gate again.

## 7. Verification Gate (before any financial table is created)

Verify in a database used only for the test, with the pinned version:

1. `users.id` is a PostgreSQL `uuid`.
2. `sessions.user_id` is `uuid`.
3. `accounts.user_id` is `uuid`.
4. The password hash is stored in `accounts`.
5. Email is stored in lowercase and is unique.
6. The adapter, with the project's table definitions, passes Better Auth's schema validation.

If the gate fails, stop and report. Do not downgrade `user_id` to `text` to make it pass.

Reason for the gate: public reports exist of the Drizzle adapter not generating UUIDs in some configurations, and the behavior in the pinned version has not been confirmed from the project's own code.

## 8. Migration and Upgrade Risks

- **Schema drift on upgrade:** new versions may add or rename columns. Mitigated by section 6 rule 7.
- **UUID generation:** see section 7.
- **Password hash format:** leaving Better Auth later requires migrating `accounts` and compatible hash verification.
- **Ownership change:** Better Auth announced on 2026-07-07 that it is joining Vercel, with a stated commitment to stay open source and framework/platform agnostic. Direction should be monitored; the `infrastructure/auth` boundary limits the impact.
- **Adapter packaging:** verified for 1.7.7: the Drizzle adapter ships as a dependency of `better-auth` (`@better-auth/drizzle-adapter`, import path `better-auth/adapters/drizzle`), so no extra package is needed. Re-check on every upgrade.
- **Email normalization and exact rate-limit table name** depend on the installed version and are confirmed by the gate and the schema generator output.
- **Auth.js migration path:** not applicable (never adopted).

## 9. Final Decision

Fintry uses **Better Auth** (exact pin) with email + password, database sessions, UUID user IDs, the `infrastructure/auth` boundary, and Drizzle Kit as the sole migration tool. Non-MVP features stay disabled. A UUID verification gate must pass before financial tables are created.
